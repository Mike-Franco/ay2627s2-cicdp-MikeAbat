# TORY-14 product deactivation implementation review

**Owner authority decision, 11 November 2026:** a Manager must have an active assignment to **every inventory linked to the shared Product** to deactivate or reactivate it. Assignment to only a subset denies both actions. All linked inventories count for this authority check, including inactive inventories. This resolves the TORY-14 lifecycle assignment scope; it does not decide other G-13 catalogue actions.

## Approved behavior and existing design

BR-028/BR-040 and G-05 Option A approve soft product deactivation by a Manager only after an atomic zero-physical-stock check across every inventory in the product's business. Quarantined units remain physical and block deactivation. Product identity and movement history remain. Ordinary transactions on inactive products are denied; Managers may reactivate. Actual, evidenced count adjustments, legitimate issues, and reasoned disposal of quarantined units are the existing approved ways to resolve stock. A false zero count is not a deactivation method.

`Product.is_active` already existed. Manual receipt, issue, Manager count adjustment, and Manager quarantined disposal use `receiving.services._lock_authorized_scope`, taking authorization locks and then Product, Inventory, and InventoryProduct locks; the helper rejects inactive products. CSV import locks all selected Product rows, then Inventory and links; its positive rows create receiving batches and its negative rows call the issue service. Scheduled expiry quarantine takes Product, Inventory, link, and batch locks but changes classification only, not physical balance. History and confirmation views do not require an active product, preserving access to prior records within assigned inventory scope.

## Implemented lifecycle boundary

The lifecycle service requires an active Manager membership and active assignments to **all** inventories linked to the same-business Product. It locks the Manager's assignment rows before the exclusive Product lock, then rechecks the complete linked-inventory set under that lock. This protects the rule against concurrent assignment changes and newly linked inventories. While holding the Product lock, deactivation checks `InventoryProduct.physical_quantity_units` across **all** links, including inactive inventories. It updates only `is_active`; existing SKU, links, batches, audits, settings, and stock remain. Reactivation uses the same authority rule and changes only `is_active`. The inventory-scoped Manager page uses POST with CSRF for either action. Staff, subset-assigned Managers, and out-of-scope direct URLs return 404. A nonzero physical balance returns a validation error without changing status.

All normal physical stock writers acquire the Product lock and recheck status. Thus receipt first commits a balance that makes deactivation fail; deactivation first makes a later receipt fail. CSV initially resolves active SKUs before its locks, so it now rechecks active status after acquiring every Product lock, rejecting a stale lookup cleanly and atomically. Its negative rows also reach the issue service's status check. Expiry quarantine remains available for historical reconciliation because it does not create or remove physical stock. Inactive history and confirmation reads remain available to authorized users.

## Committed lifecycle audit

Each actual deactivation or reactivation now inserts one `ProductLifecycleAuditEvent` inside the same PostgreSQL transaction as the Product status update. The event retains the Manager actor, business, Product, initiating inventory, prior and new active status, action, `non_demand` classification and actual timestamp. A request for the status already held is a no-op and creates no event. A failed status or audit write rolls back the transaction. The migration constrains the transition/action pair and business/Product/inventory/status consistency at insertion, and a PostgreSQL trigger rejects subsequent event updates and deletes. The event appears in the existing paginated stock history for the initiating inventory; authorized history for other inventories and the five existing stock event types keep their previous scope. This records the Product lifecycle transition without treating it as a stock movement or demand.
