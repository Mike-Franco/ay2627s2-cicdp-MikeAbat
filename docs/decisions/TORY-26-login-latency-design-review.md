# TORY-26 login latency design review

**Status:** Design analysis only, 10 November 2026. No authentication, hashing, throttle, workload, or threshold change is approved or implemented by this report.

## Decision and evidence boundary

G-07 Option A requires independent rolling limits of five failed logins per normalized identity and 20 per source IP in 15 minutes. The fifth/twentieth failure is recorded and the next attempt is denied with generic feedback. Successful login does not erase failures. G-08 fixes five ordinary route classes, including 100 login POSTs in each 500-request run, at five users and at most five in-flight requests. Each of three runs must independently meet ordinary nearest-rank p95 at or below 2 seconds; numeric forecast/reorder has a separate 3-second limit. An unexpected rejection or timeout invalidates the entire run. The recorded owner decisions impose no minimum hardware floor and do not authorize a changed workload or weaker password hashing.

`accounts/throttle.py` takes purpose-separated HMAC identity and IP advisory transaction locks in sorted order, counts indexed `LoginFailure` rows, then calls Django authentication **inside the same transaction**. On failure it inserts a row containing both keys; the transaction commits before the view creates a successful session. This gives concurrent workers a serialized count-and-record decision for both limits. A database error aborts the login; a process crash rolls back an uncommitted failure and releases the locks. A crash after a successful authentication decision but before session creation yields no session. The data rows are throttle state, not the still-open G-09 rejected-attempt security log.

The committed branch diff against `develop` has 27 files: TORY-26 requirements/validation documentation, benchmark and diagnostic scripts plus raw evidence, analyzer tests, and a repeated stock-out race test. It does not change the login implementation, password hashers, or `tests/test_auth.py`. The authentication tests use MD5 only as a test override. They check the fifth identity failure, twentieth IP failure, window boundary, generic error, CSRF, and six concurrent failures for one identity from **different IPs**; they do not test simultaneous failures from one IP across identities, worker crashes, or any proposed redesign.

The three preserved local HTTP runs have ordinary p95s of **10.774, 9.217, and 8.106 seconds**, all above 2 seconds. Login-class p95s are **12.540, 10.782, and 10.792 seconds**. The lock diagnostic measured a 5.963-second median source-IP lock call under five shared-IP clients versus 0.000363 second sequentially; up to four advisory waiters were observed. The successful-login diagnostic measured 2.626-second median sequential password verification and 10.579-second median concurrent requests; the latter spent a median 8.346 seconds in SQL calls, principally the IP lock wait. A separate 20-request, five-distinct-IP HTTP diagnostic had **6.311-second p95**. These diagnostics identify a shared-IP serialization cost, but differ in method, sample size, or conditions from the approved run and do not show that eliminating the wait meets 2 seconds. Local system load varied and was not controlled. The committed aligned CPU process aggregate is internally inconsistent with system CPU, so it cannot establish process attribution. Invalid legacy Process V2 attribution and the blocked ETW attempt are excluded from this assessment.

## Design options and risks

| Option | Potential latency effect | Security, concurrency, and crash behavior | Evidence and disposition |
| --- | --- | --- | --- |
| Keep the present transaction and measure on a controlled, quiet environment | Preserves exact current behavior. Lower background load or different approved deployment capacity may reduce hashing and lock hold times, but shared-IP successful logins remain serialized. | Locks and failure insert commit atomically across workers. Database outage fails closed; a worker crash releases locks and rolls back its uncommitted failure. A crashed attempted password check may therefore leave no recorded failure, as today. Shared networks can queue behind costly hashes and a slow worker can amplify latency. | Safest current implementation. No controlled, numeric-state three-run pass exists; do not claim the target. |
| Precheck both limits, release locks, verify password, then reacquire both locks and recheck before accepting success or recording a failure | Moves expensive hashing out of the IP critical section, so unrelated identities behind one IP could verify concurrently. | **Final recheck is essential.** Without it, concurrent wrong passwords can all read below the limit and exceed either cap. At final recheck, deny an attempt if another worker reached a limit while its hash ran; record a failure and permit a success only after both rechecks pass. Commit the failure before returning. A crash before final commit leaves no failure, as in the current design, but hashes already in flight consume CPU even when a limit becomes full. A preliminary check alone does not stop a burst of concurrent hashes; repeated requests can create hash-work denial of service unless an independently enforced in-flight bound is designed. Both keys still need stable lock ordering, including at recheck. Timing and resource behavior for unknown/inactive identities must remain materially equivalent. | Plausible redesign, **not established safe or sufficient** by current tests. Requires shared-IP and cross-worker threshold races, boundary-time tests, crash injection, bounded-work proof, and a full unchanged benchmark. Hashing alone may still miss 2 seconds. |
| Reserve an in-flight authentication slot for both identity and IP before hashing, then finalize the outcome | Can release long-lived database locks during hashing while bounding simultaneous expensive checks. | Reservations must be durable and atomically acquired for **both** keys, with no partial acquisition, and must distinguish in-flight work from failed-attempt history. They must not consume or erase the approved failure allowance. Crash recovery needs an explicit lease/expiry or fail-closed reconciliation; an early expiry could permit extra hashes or accepted failures, while a long expiry can deny legitimate users. Finalization still needs an atomic recheck and failure record. Multiple workers, clock skew, cancellation, and database outage make this substantially more complex. A process-local semaphore would not enforce the limits across workers. | Research candidate only. No reservation schema, recovery policy, or tests exist. It is not a small latency fix. |
| Shorten or partition only the IP lock, use an IP-plus-identity key, or use a non-atomic cache counter | May reduce waits in a same-IP benchmark. | Independent IP and identity limits can be exceeded if their counts and failure insert are not coordinated. Splitting an IP into identity buckets changes the approved 20/IP rule. Cache eviction, outage, restart, and inconsistent worker state can reset counts or deny users unpredictably. A hash slowdown or deferred failure write cannot be treated as a committed count. | Reject as a direct substitution for current enforcement. Any alternative needs a proved atomic shared coordinator and unchanged observable limits. |
| Reduce password hash cost, skip verification, change the IP source, change login proportion/concurrency, or drop slow/rejected samples | Could lower measured latency. | Weakens credential protection, changes abuse enforcement or the approved acceptance workload, or misstates the result. Trusting an unvalidated forwarded IP also permits spoofing and limit evasion. | Outside this review and not an acceptable path to a passing TORY-26 claim. |

## Recommendation

Retain the existing throttle and password hashing for TORY-26. A two-phase precheck/hash/final-recheck is the most plausible way to shorten shared-IP lock hold time, but the current code and tests do not establish a safe bound on expensive in-flight work, correct shared-IP races after a crash, or a 2-second p95. The distinct-IP diagnostic also shows that removing IP contention alone is insufficient evidence of a pass. Treat any redesign as later security-sensitive work with a concurrency and crash test plan, resource-abuse review, and unchanged full HTTP benchmark before adoption.

Record NFR-006 honestly as **failed for ordinary p95 in all three local diagnostic runs**. Preserve each raw run and its environment limitations; do not average, discard, or relabel samples. Report the combined page as **numeric state unmeasured** until seven complete verified Singapore dates are available no earlier than 17 November 2026. Report the valid 1,000-row CSV result separately as 5.419 seconds against its 30-second limit. Controlled-network reproducibility and hosted performance remain unverified. If a later valid, controlled run still exceeds 2 seconds, document the failed target and seek owner change control rather than silently changing hashing, limits, workload, or thresholds.
