# TORY-26 integrated validation protocol and evidence

## Source and scope

The owner-approved G-08 Envelope B in [the security and performance decision package](../requirements/SECURITY_PERFORMANCE_GAP_OWNER_DECISIONS.md) fixes 2 businesses, 4 inventories, 500 products, 2,000 receiving batches, 20,000 historical transaction rows, 5 users and at most 5 in-flight HTTP requests. The approved timing boundary is HTTP client start through complete response over a controlled local network. Each run has 20 warm-up requests per class, 500 ordinary and 500 forecast/reorder measured requests; three runs must independently meet nearest-rank p95 limits of 2 and 3 seconds. A valid 1,000-data-row CSV import has a separate 30-second completion limit. Cold starts are reported separately. There is no approved minimum hardware floor.

**Owner-approved route mapping, 9 November 2026:** use five ordinary classes at 20% each: authenticated inventory view (`GET /inventories/<id>/`), assigned Inventory products page (`GET /inventories/<id>/products/`), ordinary stock-in (`POST /inventories/<id>/products/<id>/receive/`), ordinary stock-out (`POST /inventories/<id>/products/<id>/issue/`), and login (`POST /login/`). The Inventory products page replaces the absent product-search class in the earlier proposed mix. Forecast and reorder are measured together as **one** Demand forecast page request (`GET /inventories/<id>/products/<id>/forecast/`), 500 times per run; no response is double-counted. No search or separate reorder endpoint is added. The 3 November package below this addendum retains its dated proposed wording as historical evidence.

## Benchmark execution prerequisites and recording

`scripts/tory26_http_benchmark.py` creates a fresh `tory26_benchmark_seed` database, applies migrations and calls `scripts/tory26_seed.py`. The deterministic fixture has 2 businesses, 4 inventories, 500 products, 2,000 receiving batches, 2,000 receipt and 18,000 issue audit rows, and 5 assigned HTTP users. Every run clones the seed database into a separate `tory26_benchmark_runN` database, so stock changes reset exactly between runs. A separate clone is used for CSV. The scripts refuse arbitrary database names; neither `tory` nor `tory25_manual_demo` is a benchmark write target. Capture the connected database name and counts before warm-up, the fixture manifest, raw durations, actual machine/PostgreSQL settings and client/server topology. There is no hardware minimum.

The fixture uses current-day receipts and issues and future-dated/undated batches. On 9 November, the isolated seed was activated through `manage.py activate_demand_observation 2026-11-10`; its commit-time finalization is `active`. The first eligible seven complete Singapore dates are 10–16 November, so the earliest numeric-page verification is 17 November. `scripts/tory26_prepare_coverage.py` then calls the normal assigned-Manager verification service for each previous complete date and refuses an incomplete day. No earlier date is backfilled. Until those dates exist, the combined page renders its **unavailable** state and cannot establish numeric forecast/reorder performance. Historical expiry batches also cannot be fabricated through ordinary receiving. The controlled local network here is loopback (`127.0.0.1`) and the server is Django's development server; hosted staging performance is separate.

For each of the six route classes, record 20 warm-ups separately. Preserve every measured client-start-to-full-response duration, with exactly 100 samples for each of the five ordinary classes and 500 for the single combined forecast/reorder page per run. With 500 observations, nearest-rank p95 is sorted item 475 (one-based). Report each run's ordinary and combined-page p95 independently, without pooling runs. Record server startup/first-response context outside that gate. Measure a valid, fresh 1,000-row CSV separately from upload start to complete response, and verify stock, success marker and audit outcome. The owner approved on 9 November that an unexpected rejected response or timeout invalidates the whole run. The runner records the failing class, sample, error/status and aborts; it never drops or retries just that sample. A fresh full run is required after fixing the cause or conditions. The runner requires numeric forecast and reorder output before warm-ups, so unavailable-state timing cannot be labeled a passing numeric run.

The previously proposed 2 vCPU/4 GiB floor is not an approved requirement. This local benchmark is separate from hosted evidence and the TORY-19 one-hour staging scheduler check.

### Login latency diagnosis and numeric-state gate

The original three runs remain diagnostic evidence without changed samples or thresholds. The runner starts the timer after taking each client's lock, so its own thread queue is excluded. [Raw login diagnostic evidence](../../benchmark-results/tory26-login-diagnostic.json) from an isolated clone records three sequential successful Django test-client login POSTs at a 2.666-second median: password verification 2.626 seconds, all SQL 0.018 seconds, and Django session login 0.009 seconds. With five simultaneous clients sharing loopback source IP, 20 successful POSTs had a 10.579-second median: password verification 2.101 seconds per request, while SQL time rose to 8.346 seconds, primarily waiting on the PostgreSQL IP advisory lock held through authentication. Five direct password verifications in parallel took 2.665–2.922 seconds each. An earlier repeat on the same isolated clone measured 1.522-second sequential and 7.433-second five-client medians, showing local load variability. The root cause is the shared-IP throttle lock serializing five deliberately expensive password checks, with password hashing itself close to or above the 2-second ordinary threshold on this PC. No authentication, rate-limit, middleware or hashing behavior was weakened. Distinct-source-IP benchmarking remains a possible controlled-condition investigation, not a passing result.

A later [per-lock diagnostic](../../benchmark-results/tory26-lock-diagnostic.json) used a separate seed clone and timed each original `pg_advisory_xact_lock` SQL call through Django's per-connection execute wrapper. Three sequential and 20 five-client, shared-loopback successful logins yielded identity-lock medians of **0.000934 / 0.000724 seconds** and source-IP-lock medians of **0.000363 / 5.963320 seconds**, respectively. Median whole-request times were **1.581 / 7.460 seconds**. A read-only `pg_stat_activity` sampler saw advisory-lock waiters in 458 of 481 samples and up to four waiting sessions. Windows system CPU was **41.67% median during the three-second idle baseline** (11 samples), **46.73% sequential** (20 samples), and **42.19% concurrent** (117 samples). The CPU figures include all system processes; the run-phase values are not background-only measurements. The per-call timer includes PostgreSQL round-trip and lock waiting, and the polling sampler is observational rather than an exact server-side wait clock. This diagnostic confirms that the common IP lock, rather than the per-identity lock, accounts for the extra concurrent SQL time. It does not replace any approved HTTP sample or establish a passing threshold. The previous raw evidence files were not overwritten.

### Later CPU and distinct-source-IP diagnostics

The initial three-second idle CPU sample was too short to attribute background load. A [longer process-sampled idle record](../../benchmark-results/tory26-cpu-idle-diagnostic.json) measured 48.74% median system CPU, but its seven PowerShell process snapshots imposed about 32 CPU seconds of observer work over 63.61 seconds. A [quieter two-snapshot record](../../benchmark-results/tory26-cpu-idle-quiet.json) measured **61.07% median system CPU** over 92 half-second samples and a 37.45-second process snapshot span. Its PowerShell observer used 6.28 CPU seconds, about 1.40% of 12-logical-processor whole-machine capacity; Chrome, Code, Discord and other visible processes also used CPU. All matching process snapshots together accounted for only 10.42% of whole-machine capacity, so this method cannot fully attribute the system-wide busy time. Short Windows performance-counter checks separately showed roughly 49.5–67.2% total CPU, with about 28.8–37.3% privileged time and low DPC/interrupt time. The sustained system load exists without Tory benchmark requests; no unrelated process was stopped or modified.

Windows accepted locally bound connections from `127.0.0.2` through `127.0.0.6`, making a separate-source-IP login diagnostic feasible without Tory code changes. A [separately labeled HTTP diagnostic](../../benchmark-results/tory26-distinct-ip-diagnostic.json) sent 20 successful `POST /login/` requests from those five addresses to a fresh isolated clone. All returned HTTP 302, stock evidence counts were unchanged, and the client verified each bound socket source address. Median latency was **5.803 seconds**, with a 20-sample nearest-rank p95 of **6.311 seconds**. This is not the approved ordinary workload, not a controlled comparison at equal background load, and not a performance pass. The earlier shared-loopback failures remain intact; the isolated diagnostic clone was removed afterward.
